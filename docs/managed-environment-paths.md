# 托管运行环境存储布局与固定路径

适用范围：`src/runtime/vibeocr/runtime/environments/managed_environments.py` 与
`managed_cleanup.py`（多环境管理存储）。本文只描述磁盘布局与升级/迁移策略，
接口契约以代码与测试为准。

## 固定路径布局

- 每个环境的 venv 直接位于唯一固定路径 `environments/<id>`，升级前后不变；
  新环境的 `id` 为名称/用途派生的可读 slug（碰撞追加 `-2`/`-3`），不再生成 UUID，
  也没有 `revisions/<N>` 或随机后缀层级，减少 Windows 路径长度压力；这是存储布局的
  根因修复，不是 UI 截短。
- 安装/修复事务使用两个固定槽位（每环境各一个，绝不随升级次数累积）：
  - `environments/.staging/<id>`：候选 venv 构建位置；
  - `environments/.retired/<id>`：换入时旧 venv 的整体退役位置。
- 每环境私有状态（缓存/模型/临时目录）仍在固定路径 `state/environments/<id>`，
  与 venv 位置无关。

## 安装事务与崩溃恢复

1. 候选在 `.staging/<id>` 构建后先在 staging 探针（锁外、可取消）；
2. 提交在 store 锁内按序执行：journal 落盘（`state/environment-swaps/<id>.json`）
   → 旧 venv 移入 `.retired/<id>` → 候选换入固定路径 → 在最终路径复检探针
   （兜底 venv 随目录迁移的绝对路径/relocation 破损；入口均按 `python -m`
   启动，不依赖控制台脚本）→ 注册表原子提交 → 清除 journal；
3. 换入失败时回滚目录与归属；若文件占用阻碍回滚，保留 journal 并保护相关目录，待占用解除后恢复；
4. 崩溃中断：journal 保留，下一次 `list`/安装/切换/清理在
   `_recover_pending_swap` 中以**注册表提交为分界**收敛——注册表记录
   等于候选即提交已完成，只收尾清除 journal；否则一律保守回滚（不前滚
   候选），旧副本/原缺失状态复位；回滚可重入，清除失败保留 journal 与
   保护，下次扫描重试。

## 归属与清理保护

- cleanup ledger 只登记产品自建路径；换入退役时仅**镜像**既有归属记录，
  未知/未登记数据随目录移动但不获得可删除归属；
- 退役槽位回收时只删除已登记子树，存在未登记数据时 fail closed
  （提示走空间清理预览或人工检查），不推断归属、不删除未知数据；
- 存在 pending journal 的环境，其全部路径在清理扫描中一律受保护；清理
  计划冻结证据包含 journal 状态，preview 与 run 之间 journal 变化即失效。

## 旧环境升级与迁移策略

- 历史 `<id>/revisions/<N[-hex]>` 布局的记录（含旧 UUID id）照常读取，
  仍受支持的配方可启动、切换与清理，不做后台自动迁移；
- RapidOCR／RapidTable 配方已退役。用户自建旧环境及其模型保留，不自动删除，
  也不能直接当作 Paddle 环境启动；当前默认环境使用 `paddleocr-ort-cpu`，
  从随产品携带的离线依赖与默认文字模型准备；离线依赖来自共享 wheel pool
  （base / CPU / DirectML 闭包去重分发一次），各环境按自身锁的精确清单
  在独立缓存目录解包安装；
- 从旧版升级且仍选中退役默认环境时（`rapidocr-cpu` id，或名称为“默认环境”的
  历史 32 位 UUID），另建离线 Paddle 默认环境；安装失败时保留旧环境并可续装。
  新服务健康切换后，通过既有空间清理事务删除被替代环境的已登记目录，
  不删除共享模型缓存、未知目录或用户自建环境。文件占用等清理失败不会撤销
  健康服务；待清理记录持久保存，下次成功切换至替代环境时续做。
  失败重试不重复建环境；已有同名目录或环境保持不动，用户另选的环境不被覆盖；
- 对旧布局环境重新安装即迁移：旧目录树整体移入 `.retired/<id>` 原样保留
  （内部内容不变），新 venv 落在固定路径 `environments/<id>`，历史 UUID id 保持不变；
- 退役树中的已登记旧版本目录可通过空间清理回收；未知目录永远保留，
  且会阻止后续换入复用该退役槽位，待人工处理；
- 不存在无界累积：新布局下每环境最多一个 staging 与一个 retired 槽位，
  下一次安装/修复会按 ledger 回收复用。


## 能力目录与准备目标

Runtime `list.recipes` 显式投影 `engine`、`family`、`family_display_name`、
`provider`、`target_device` 与远程服务宿主能力；显示名和 recipe id 不承担设备匹配。
C# bridge 与现有 Settings 页面仅消费这些字段。下载来源的 `provider` 同样由
Runtime 适配表提供，前端不拼接或拆分来源 id。

`find_compatible` 是只读查询：显式目标优先且不被其他候选替代；未指定目标时
优先当前兼容环境，再按 id 稳定排序。`prepare_target` 才允许创建纯解释器环境，
其 recipe → 精确环境 id/名称预留保存在注册表可选 `prepare_targets` 字段中；
创建中断、失败重试和宿主重启均复用该预留，不按显示名认领用户环境。用户把
该目标安装为另一能力后，原环境完整保留，下一次准备分配新的归属。准备目标
成为 `find_compatible` 未选中的活动已安装环境（scope 锁过期或闭包损坏）时
同样保留该环境并另分配可维护的受控目标，重复准备与宿主重启复用新归属，
不重复创建；健康兼容目标仍由 `find_compatible` 零安装复用。删除环境时在
同一删除事务内终结该对象的准备归属与落盘安装计划：同 id 同名重建的新对象
不会被旧 plan 的 revision/CAS 冒认，须重新预览。
准备不安装业务依赖或模型，确认后的安装仍使用已有 plan/revision/source CAS。
默认随包离线环境初始化与用户显式创建空环境保持不同入口。

环境快照的 `operation_blocks` 给出动作及阻止原因（null 表示快照允许）；实际
执行仍重核引用、锁、活动指针和修订。依赖、模型、服务分别投影；模型未检查
保持 `not_checked`，设备/provider 声明不代表已完成该设备的模型推理。

旧注册表缺少新增字段时继续读取；不迁移或删除未知目录、历史结果与缓存。
若需要回退到不识别 `prepare_targets` 的旧二进制，应先停止产品并备份注册表，
仅移除该可选归属索引；环境记录、revision、路径和所有环境目录保持原样。
回到新版后，原环境仍可手工选择和切换，已安装兼容环境仍按目录复用。
